# HR Strategy Copilot

**인사기획 담당자의 제도 설계 업무를 위한 RAG + 멀티에이전트 의사결정 지원 시스템**

인사 데이터에서 문제를 찾아내고, 사내 규정·법령·업계 사례를 검색해 근거를 붙이고,
대안을 비교해 인사위원회 상정용 개편안 초안까지 만든다.
**모든 문장에 근거 인용이 강제되고, 근거 없는 주장은 파이프라인이 반려한다.**

```bash
pip install -e ".[dev]" tabulate
hrx data && hrx index
hrx brief "반도체사업본부 차장 승진 적체를 어떻게 해소해야 하나?" --stdout
```

LLM API 키가 없어도 전체 파이프라인이 동작한다(결정론적 폴백 경로). 키가 있으면
CrewAI 5-에이전트 경로로 자동 전환된다.

## 1. 왜 이 문제인가

인사기획 직무의 실제 업무는 대체로 이런 모양이다.

> "우리 차장 적체 심한데, 다른 데는 어떻게 했대? 돈은 얼마나 들고? 법적으로 걸리는 건 없고?
> 그래서 뭘 하자는 건데?"

이 한 문장에 네 가지 일이 섞여 있다 — **진단(데이터)**, **벤치마크(문서 검색)**,
**영향 추정(시뮬레이션)**, **절차 검토(법령)**. 담당자는 이걸 스프레드시트, 규정집 PDF,
컨설팅 리포트, 노무법인 메일을 오가며 며칠에 걸쳐 수작업으로 조립한다.

이 시스템은 그 조립 과정을 파이프라인으로 만든다. 핵심은 "AI가 대신 결정한다"가 아니라
**"결정의 재료를 근거와 함께 30초 만에 모아 준다"** 는 것이다.

### 2.1 RAG — 규정 문서에 맞춘 설계

일반적인 "고정길이 청킹 + 임베딩 코사인" 대신 규정·법령 문서의 성질에 맞춰 네 군데를 바꿨다.

**① 조항 인식 청킹** (`rag/chunking.py`)
규정에서 인용의 최소 단위는 "제N조"다. 청크가 조 경계를 넘으면 `[INT-HR-002§제5조]` 같은
인용이 무의미해진다. 마크다운 헤딩으로 1차 분할하고, 조항 제목에서 조 번호를 추출해
메타데이터로 박고, 긴 조는 항(①②③) 경계에서만 2차 분할한다.

**② 하이브리드 검색 + RRF** (`rag/retriever.py`)
BM25(어휘 정확 매칭)와 char n-gram TF-IDF(어미 변형·복합명사 부분 일치)를 병렬로 돌리고
Reciprocal Rank Fusion 으로 합친다. 점수 스케일이 다른 두 신호를 가중합으로 섞으면
하이퍼파라미터에 민감해지지만, 순위만 쓰는 RRF 는 튜닝 없이 안정적이다.

**③ BM25 길이 정규화 완화 (b=0.75 → 0.4)** (`config.py`)
기본값 b=0.75 는 짧은 조문을 과도하게 우대한다. 규정 코퍼스는 조문 길이 편차가 커서
(짧은 정의 조항 ↔ 긴 해설 조항) 이대로 두면 핵심 조문이 밀려난다.
이 한 줄이 골든셋 recall@6 를 크게 바꿨다.

**④ 코퍼스 라우팅 + 하드 카테고리 필터**
"불이익 변경인가?" 는 법령 코퍼스를, "우리 규정에 뭐라고 돼 있지?" 는 사내 코퍼스를 본다.
법적 제약을 뽑을 때는 질의를 분리해 법령 카테고리만 하드 필터링한다 — 사용자 질문 문장만으로
법령을 검색하면 주제와 무관한 조문(예: 승진 질의에 개인정보 조항)이 상위로 올라온다.

> **형태소 분석기를 쓰지 않은 이유**: konlpy/mecab 은 JVM·빌드 의존성이 있어 CI 에서 깨진다.
> 대신 어절 토큰 + 조사 절단 휴리스틱을 쓰고, 부분 일치는 char n-gram TF-IDF 에 맡겨
> 역할을 분리했다. (`rag/tokenize.py`)

### 2.2 Harness — 에이전트를 믿지 않는 장치

LLM 출력을 그대로 신뢰하지 않는다. 세 겹의 장치를 둔다.

| 장치 | 파일 | 하는 일 |
|---|---|---|
| **구조화 스키마** | `harness/schemas.py` | 단계별 Pydantic 모델. 필수 필드 누락·형식 오류를 파싱에서 차단 |
| **근거 게이트** | `harness/guard.py` | 인용률이 기준 미달이거나 없는 근거를 지어내면 **실패 사유를 담아 재시도** |
| **컨텍스트 예산** | `harness/budget.py` | 섹션별 우선순위·최소 보장량으로 패킹, 다음 단계엔 `compact()` 로 축약 전달 |

근거 게이트의 재시도 루프가 핵심이다.

```
생성 → JSON 파싱 → 스키마 검증 → 근거 검증
                       │              │
                       └─ 실패 시 오류 메시지를 프롬프트에 되먹여 재시도 (최대 2회)
                                      │
                       한도 초과 시 → 예외가 아니라 명시적 실패 객체 반환
                                   → 상위에서 결정론적 폴백 경로로 전환
```

**조용히 틀리느니 시끄럽게 폴백한다.** 인사 제도 문서에서 근거 없는 법적 판단 한 줄은
보고서 전체의 신뢰를 무너뜨린다.

### 2.3 멀티에이전트 (CrewAI)

| # | 에이전트 | 도구 | 출력 스키마 |
|---|---|---|---|
| 1 | 현황분석가 | `org_diagnostics`, `hr_search`, `pay_equity` | `Diagnosis` |
| 2 | 법령벤치마커 | `hr_search(corpus=external)` | `Benchmark` |
| 3 | VOC분석가 | `voc_analysis` | `VocInsight` |
| 4 | 제도설계자 | `workforce_simulation`, 대안 카탈로그 | `PolicyProposal` |
| 5 | 검증관 | `hr_search(절차 규정)` | `ComplianceReview` |

도구는 전부 **순수 파이썬 함수**다(`agents/tools.py`). CrewAI 에 의존하지 않으므로
단위 테스트가 가능하고, LLM 없는 폴백 경로에서 같은 함수를 그대로 쓴다.
모든 도구는 인용 키를 함께 돌려준다 — 문서는 `INT-HR-003§제4조`, 정량 결과는 `DATA§보상형평성`.
덕분에 "숫자는 맞는데 출처가 없는" 문장을 기계적으로 걸러낼 수 있다.

## 3. 데이터

실제 기업 인사 데이터를 쓸 수 없으므로 가상 제조기업 **한빛전자**(846명, 99개 조직)를 합성했다.
무작위 잡음이 아니라 **분석이 잡아내야 할 문제를 의도적으로 심어 두었다.**

| 심어 둔 문제 | 데이터 조작 | 탐지 지표 | 탐지 결과 |
|---|---|---|---|
| 승진 적체 | 반도체 본부 차장 체류연수 상향 | 체류연수 ÷ 표준연수 ≥ 1.5 | 8.46년 / 5년 = **1.69배** |
| 평가 관대화 | 디스플레이 본부 등급 커브 변경 | S·A 비율 편차 ≥ 10%p | 55.6% vs 전사 27.7% (**+27.9%p**) |
| 보상 역전 | 경력 입사자 밴드 프리미엄 | 입사경로별 침투율 격차 > 8%p | G3 **+11.7%p**, G4 **+11.1%p** |
| 승계 공백 | 일부 핵심 보직 후보 0~1명 | 커버리지 기준 미달 | 12개 중 **6개 위험** |
| 과대 조직 | 6개 팀 정원 과다 배정 | 팀 인원 > 15명 | 76개 팀 중 **16개** (최대 27명) |

**문서 코퍼스** — 9개 문서 / 107개 청크

- 사내 규정 5종: 인사규정, 성과관리 운영지침, 보상체계 운영지침, 리더십 파이프라인 운영지침,
  조직운영·인원계획 세칙 (모두 조항 구조로 작성)
- 외부 4종: 근로기준법 요지, 관련 법령 요지(고평법·기간제법·고령자고용법·근참법),
  HR 트렌드 노트, 제도 개편 사례집

> ⚠️ 법령 문서는 **학습·데모용 요지 정리본**이며 법령 원문이 아니다. 문서 자체와 생성되는
> 모든 보고서 하단에 이 경고가 붙는다. 실제 적용 시 국가법령정보센터 원문과 노무 전문가
> 검토가 필요하다.

## 4. 평가

"검색이 좋아졌다"를 눈대중이 아니라 숫자로 관리하기 위한 골든셋(20문항)과 평가 하네스.

```bash
hrx eval
```

| 지표 | 값 | 설명 |
|---|---|---|
| recall@6 | **1.000** | 정답 근거가 상위 6건 안에 있는 비율 |
| MRR | **0.843** | 정답 근거의 평균 역순위 |
| route accuracy | **1.000** | 질의 → 코퍼스 라우팅 정확도 |
| theme accuracy | **1.000** | 질의 → 제도 테마 분류 정확도 |
| citation coverage | **0.711** | 생성된 보고서의 사실 주장 중 근거가 붙은 비율 |
| hallucinated citations | **0** | 인덱스에 없는 근거를 지어낸 건수 |

CI 는 `hrx eval --min-recall 0.90` 을 게이트로 걸어 검색 파라미터 변경이 품질을 떨어뜨리면
빌드를 실패시킨다.

**개발 중 평가 하네스가 잡아낸 실제 버그**: SQLite 로드 시 `ORDER BY doc_id` 로 정렬해
BM25 행렬의 행 순서와 어긋났고, 그 결과 **점수가 엉뚱한 청크에 붙고 있었다**(recall 0.75).
`ORDER BY rowid` 로 고치고 인덱스에 청크 ID 지문을 저장해 불일치 시 자동 재구축하도록 했다.
눈으로는 "결과가 그럴듯해서" 못 잡았을 버그다. (`rag/index.py`, `tests/test_rag.py`)

## 5. 사용법

```bash
hrx data                    # 합성 인사 데이터 생성
hrx index                   # RAG 인덱스 구축

hrx search "평가 등급 배분율을 강화하면 불이익 변경인가?"   # 점수 내역까지 표시
hrx diagnose --detail                                    # 조직진단 지표
hrx simulate --years 3                                   # 인원·인건비 시나리오
hrx succession --detail                                  # 승계 커버리지 + 9-Box

hrx brief "경력입사자 연봉 역전 문제를 어떻게 풀까?" --stdout
hrx eval                                                 # 검색·근거 품질 평가
```

**대시보드** (5개 탭: 조직진단 / 인력·인건비 / 승계 파이프라인 / 근거 검색 / 제도 개편안)

```bash
pip install -e ".[app]"
streamlit run src/hrx/app/dashboard.py
```

**LLM 연결** — `.env.example` 을 `.env` 로 복사하고 키를 채우면 CrewAI 경로로 전환된다.

```bash
ANTHROPIC_API_KEY=sk-ant-...   # 또는 OPENAI_API_KEY
HRX_LLM_PROVIDER=auto          # auto | anthropic | openai | none
```

```markdown
## 6. 법적·절차적 검토
| 직급 통합 | ●●● 높음 | `EXT-LAW-001§제93조` | 취업규칙 기재사항 변경 — 의견청취(불이익 시 동의) |
```

추천 규칙은 명시적이다: **① 법적 위험이 낮을 것 ② 인건비 압박이 작을 것.**
구조적으로 더 근본적인 대안(직급 통합)은 절차 부담이 크므로 로드맵 후속 단계로 배치한다.

## 8. 설계 판단 기록

이 프로젝트에서 내린 판단과 그 이유.

**임베딩 모델을 안 썼다.** 문서가 107청크 규모이고 도메인 용어(침투율, 체류연수, Ready Now)가
많다. 이 조건에서는 어휘 매칭이 의미 매칭보다 강하다. 임베딩을 붙일 자리는 `rag/index.py` 에
훅으로 열어 뒀지만, 기본값은 오프라인 동작이다. 데모가 API 키와 네트워크에 의존하면
포트폴리오로서 재현되지 않는다.

**폴백 경로를 "예비"가 아니라 "일급 경로"로 만들었다.** CrewAI 경로와 같은 도구, 같은 스키마,
같은 검증을 쓰고 다른 것은 문장을 누가 쓰느냐뿐이다. 그래서 (a) API 키 없이 CI 가 돌고
(b) LLM 단계가 실패해도 부분 대체가 가능하며 (c) 평가 하네스가 검색·근거 품질만 분리 측정할 수 있다.

**개인 단위 예측을 인사 판단에 쓰지 않았다.** `talent_at_risk()` 는 이탈 확률을 예측하는
모델이 아니라 **리더 면담 대상 선정용 조직 운영 지표**다. 개인 예측 결과를 인사 불이익에
직접 쓰는 설계는 법적·윤리적 위험이 크고, 코드 주석과 대시보드 캡션에 이를 명시했다.

**법적 판단을 단정하지 않는다.** 에이전트 시스템 프롬프트와 폴백 템플릿 모두
"~에 해당할 수 있다 / 검토가 필요하다" 형태만 쓰도록 강제했다. 시스템이 "위법"이라고
단정하는 순간 실무에서 쓸 수 없는 도구가 된다.
